## 原因和最小修复

原私有运行器在解码器实例上安装`replay_order`记录函数。该函数通过闭包引用原绑定方法及求解器，形成`solver→decoder→recording closure→solver/decoder`环。评价函数返回后，大量解码缓存因此仍存活，释放工作可能推迟到后续垃圾回收或解释器退出阶段。

虚构数据及只读诊断证据：单独审计旧大轨迹文件后，发送结果至退出约0.020秒；对1500个虚构候选关闭自动GC观察生命周期，旧评价函数返回后求解器仍存活，显式GC回收12,154,988个跟踪对象、耗时3.032890秒。移除实例记录钩子后，求解器通过引用计数于0.892895秒内释放，随后GC回收0个对象，发送结果至退出约0.021964秒。这些是定位引用问题的单次观测，不是算法性能基准或稳定加速比。

修复包装冻结评价器，仅在查询结束后清空`decode_cache`、`micro_cache`、`board_term_cache`，并删除解码器实例的`replay_order`覆盖，恢复类方法解析。没有在搜索过程中清缓存，也没有把原绑定方法重新存入实例而形成新的自引用。所有清理成本在结果发送前、同一个总预算内计入；成功返回前验证求解器已不再存活。异常时释放重缓存但保留原始错误。没有强制全局GC、硬退出或放宽退出宽限。

关键清理操作为：

```python
solver.decoder.decode_cache.clear()
solver.decoder.micro_cache.clear()
solver.decoder.board_term_cache.clear()
solver.decoder.__dict__.pop("replay_order", None)
```

实际实现还以弱引用验证对象释放并记录清理起止时间；正常路径中，这些操作发生在所有候选评价和最终布局转换之后。诊断器和详细轨迹保留本地，生产算法源码未变。
